How good are language models at writing regular expressions you could actually ship? Most benchmarks ask only whether the pattern passes its tests. This one asks whether you’d dare deploy it.

Two examples explain the whole thing

A model gets a plain-English description and writes a regex. Then we check it three ways. Both answers below score 100% on correctness — and neither is shippable.

“Matches 5 numeric digits, such as a zip code.”

\b\d{5}\b

Passed every test it was given. Still wrong — and here is the string that proves it:

"\n00000"

The reference is ^\d{5}$. The model’s version also matches a zip code sitting on the second line of a multi-line string. Whether that matters depends on your input — which is why the benchmark reports it rather than silently calling one of them right. 806 answers passed their tests while describing a different language than the reference.

“tests the validity of a domain or hostname”

^([a-zA-Z0-9]([a-zA-Z0-9\-]{0,61}[a-zA-Z0-9])?\.)+(com|org|net|mil|edu)$

Passed every test. Also a denial-of-service bug:

a quantifier wraps a quantified group — exponential backtracking on a failing suffix

A realistic, production-looking pattern — and exponentially exploitable. Put it on a signup form and you have a denial-of-service bug. 135 such patterns appeared across the run: correct, and unsafe.

What the pilot showed

01

Correct is not usable, and the ratio is 4×

gpt-4o-mini passes 40% of tasks and only 10% are usable. A fifth of its patterns are ReDoS-vulnerable; others pass the examples they were given while being provably a different language from the reference. A leaderboard reporting correctness alone would rank this model four times better than it deserves for anything that touches untrusted input.

02

A pinned provider that fails is visible, not substituted

mistral-small-3.2 returned nothing usable across all ten tasks: DeepInfra was rate-limited upstream (engine_overloaded), and because the request set allow_fallbacks: false, OpenRouter refused to quietly reroute to another provider serving different weights at a different quantization.

That is the designed outcome. It is reported as a response-failure rate with the model left in the table, rather than dropped — a visible failure beats an invisible substitution.

Two further findings — how output formatting swung one model’s score by 20 points, and why nobody reproduced the reference exactly — are in the appendix, along with the metrics that need more than a sentence to explain.

Controls

Three synthetic predictions ride the identical scoring path in every model's run, because a scorer silently returning zeros looks exactly like a model that failed. All four models' controls came back as expected — including mistral-small, which is how we know its zeros are a collection failure and not a scoring one.

Check it yourself

Every model response is committed. The scores come from those files and nothing else — no API key, no cost, no need to trust us. 

git clone https://github.com/plicara/regexeval-2026
cd regexeval-2026
make setup    # pinned scorer + corpus
make score    # recomputes every number above

make check does the same and fails if the numbers drift from what’s published. It runs in CI on every push, so this page cannot quietly disagree with its own evidence.
